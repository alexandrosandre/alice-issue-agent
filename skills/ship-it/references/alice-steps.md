# Alice's /ship-it steps

Alice's sessions add an independent risk review and functional verification to /ship-it, because her PR's reviewer did not watch the work and has no local stack of hers to try it on (design D29, `docs/design.md`). They keep their state in `RISK_DIR` as alice-assess-risk resolves it, where /create-pr reads it: `risk-section.md` (the Risk section, with what was verified), `level.json` (the risk level and its title for the PR's first line) and `share_url` (the live-questions link, which step G writes). The two skills write and re-render the first two themselves. The final summary also gives the risk level and what could not be verified.

Before /ship-it's step 1:

- **A. Risk review, first pass:** `alice-assess-risk` on the branch's changes against a freshly fetched `origin/master`, run from a foreground general-purpose subagent given only the inputs that skill lists. It is independent only while it never sees this session's reasoning. Its answers set the risk level and the verification plan, and its riskiest changes, which stay out of the PR, are cases the verification exercises.

After /ship-it's step 1 first runs, once its review's fixes are in, so the evidence is captured on reviewed code:

- **B. Functional verification:** `alice-verify-change` at the level step A set. Commit first (no push), because the evidence names the commit it verified. Fix what it finds and verify again; it records the evidence and re-renders the Risk section.

After /ship-it's last step:

- **C. Re-verification:** when a commit after the one the evidence names (`$RISK_DIR/evidence.json`) changed what the verified flows run, a fix or a base merge that changed code they call, run `alice-verify-change` once more, at the same level, on the PR's pushed head, and replace the evidence. Docs and comments change nothing. If it finds a bug, fix it, take the fix through /autoreview, and verify that head instead.
- **D. Risk review, second pass:** `alice-assess-risk` in a fresh subagent as in step A, now also given the first pass's verification plan and the evidence; it re-renders the Risk section. If it raises the level, run `alice-verify-change` at the new level, which writes the evidence for every requirement of that level; a bug it finds goes through step C's fix loop, and the second pass then runs again on the fixed head. Each of its riskiest changes the evidence does not cover goes in `not_verified`, one line each, as in the first pass. Then run the checks in its "Before merging" list that your rails allow (a read-only query, a build, a test) and tag each run or screenshot that settles one with `settles` and the item's text verbatim, so the list shows it ticked with its proof (a tag whose item the list no longer holds ticks nothing: tag again from the new list); the rest stay for the person reviewing, and a check that fails is a bug for step C's fix loop.
- **E. Preview:** at the level step D settled, 3 Elevated or 4 High. When the PR touches none of the paths the preview workflow watches, mark the preview not applicable in the evidence: a preview deploys only what those paths build. Otherwise add the `preview` label through REST when the PR does not have it yet (`gh api -X POST repos/<org>/<repo>/issues/<pr>/labels -f 'labels[]=preview'`), and add the preview URL to the evidence (design D28): `https://<branch-slug>.preview.example.com`, with the slug computed as the preview workflow computes it. Do not wait for the deployment: the workflow's comment on the PR shows its status to the reviewer, who retries a failed one. The label also keeps the preview rebuilt on later pushes that touch those paths and removes it when the PR closes.
- **F. Description:** render the Risk section again with the final evidence, regenerate the title and description as /create-pr writes them, and update the PR with `python3 scripts/github/rest.py pr-edit` alone: a base merge or push now would restart the review bots after /autoreview stopped watching them.
- **G. Live questions:** share this session behind the PR description through the team's session-sharing link (design D42), so a reviewer can ask about anything you did and get an answer at once, while a GitHub review reaches you for a round. Save the PR's current `title` and `body`, from `python3 scripts/github/rest.py pr-view <pr>`, to files in `$RISK_DIR` (`mkdir -p` it: a round that skipped step F has none), and run the sharing CLI on the current session with the title and the body as its summary, both passed through their files because backticks in them would run in the shell, without asking anyone; the CLI redacts secrets before uploading. Write the link to `$RISK_DIR/share_url`, then change only the PR's "ask live" line in that body: replace it, or add it after the header lines /create-pr writes (issue references, preview, recordings) as `Use GitHub reviews to ask, comment or approve; or ask live: <link>`, and update it with `rest.py pr-edit`. A review round in a new session holds none of the earlier risk files, so rebuilding the description there would drop its Risk section. Sharing again in the same session publishes a new version at the same link; a round in a new session gets its own link, which replaces the old one. When the CLI is missing or refused, leave the line out and say so in the hand-over.
